Nova Ed-Fi Core

Version 1 — Architecture & Scope

Nova Project · Design reference (pre-implementation) · July 2026

Executive Summary

Version 1 should be as small as possible. Do not solve PEIMS yet. Build a rock-solid Nova Ed-Fi Core — infrastructure that connects to any Ed-Fi ODS the same way, whether the district runs eSchoolPlus, Skyward, Ascender, Infinite Campus, or PowerSchool.

The Ed-Fi layer must know nothing about Texas, attendance, Special Education, or PEIMS rules. Its job is to connect to an Ed-Fi API reliably and expose data in a clean, consistent way. PEIMS and other domain modules plug in above this layer.

Design Principle: Two Layers, One Boundary

PEIMS / TSDS / Texas rules (future) sit above Nova Ed-Fi Core. The core handles auth, HTTP, paging, discovery, change versions, and diagnostics. Any vendor that exposes Ed-Fi is reachable through the same client API.

Ed-Fi SOCKS — Self-Configuring Compatibility Probe

SOCK (System Optimization and Compatibility Check) today scans hardware and recommends models. Ed-Fi SOCKS scans an endpoint and builds a capability profile.

When an operator provides https://district.ed-fi.org, Nova automatically:

  1. Resolves base URL, TLS, and reachability
  2. Detects authentication mode
  3. Detects Ed-Fi API and data model version
  4. Pulls metadata and available resources
  5. Tests paging on a safe sample resource
  6. Probes change-version and delta endpoint support
  7. Measures latency
  8. Writes nova.edfi_capability.v1 profile to runtime
  9. Surfaces health issues if anything fails

No configuration wizard. Nova learns the environment.

Capability Profile Contract

{
  "schema": "nova.edfi_capability.v1",
  "connection_id": "district-main",
  "base_url": "https://district.ed-fi.org",
  "api_version": "3.5.0",
  "data_model_version": "4.0.0",
  "auth": { "type": "oauth2_client_credentials", "ok": true },
  "features": { "paging": "offset-limit", "change_versions": true },
  "resources": ["schools", "students", "studentSchoolAssociations"],
  "latency_ms": { "token": 180, "metadata": 95, "sample_get": 310 },
  "health": "ok"
}

Public API Surface (Conceptual)

client = EdFiClient.from_connection("district-main")
client.test_connection()
client.discover()

client.change_version()
client.delta_since(last_version)
client.health()

No get_peims_attendance(). No Texas field maps. No TSDS codes.

What Not to Build in V1

  • PEIMS-specific resources or transforms
  • Vendor branching inside Ed-Fi Core
  • Full sync scheduler / ETL
  • Configuration wizards
  • Write-heavy ODS operations (keep V1 read-first)

Suggested Build Order

  1. Contracts + config
  2. Auth + connection test
  3. Discovery
  4. GET + paging
  5. Diagnostics + audit JSONL
  6. Compatibility probe (Ed-Fi SOCKS)
  7. Tools + health payload
  8. PEIMS lane as separate consumer (later)

Connection Identity

  • connection_id as the stable handle
  • Credentials in local config only
  • Profile regenerated on probe, not hand-edited
  • PEIMS uses connection_id, not raw URLs

How PEIMS Plugs In Later

PEIMS uses Ed-Fi Core to fetch standard resources. Texas rules and collection mappings live in a separate domain layer — never inside services/edfi/.

Next Step Before Coding

Start with config, auth, and discovery only. Stop for a real sandbox connection test before paging or change tracking.
